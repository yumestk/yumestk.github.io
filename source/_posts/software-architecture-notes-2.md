## 为什么要画图

画架构图不是为了装逼，而是为了让别人和你看到的是同一个系统。

所有人看着同一张图说话 = 我们说的是同一个东西。想清楚了却讲不明白几乎等于没想清楚。同时画架构图也有助于我们理解一个项目的数据流转，所以我们得自己尝试画好架构图，画图的本身就是一种思考，当你试图把脑中的系统画下来，常会发现“诶，这里边界在哪”，“诶，两个东西谁依赖谁”，画图会逼你把含糊的地方想明白

仔细想想，画图其实有点像给自己的架构理解做一次单元测试。

嘴上说着“用户请求经过某某模块，然后把结果写入数据库”，好像整个流程已经烂熟于心。但真要把这些东西画出来，就可能突然卡住：这个模块为什么需要调用另一个模块？它们之间传递的究竟是什么？这个操作失败了，谁负责处理？如果连一根箭头都解释不清楚，那可能不是画图技术的问题，而是压根没想明白这部分设计。（说的就是我自己）🫨

## 烂图四宗罪

```text
┌─────────────────────────────────────────────────────────────┐
│  烂图四宗罪                                                    │
├─────────────────────────────────────────────────────────────┤
│  ① 没有边界    所有框平铺在一起,分不清哪些在一个进程/         │
│                一台机器/一个信任域里。                         │
│                                                              │
│  ② 箭头没方向  线就是线,不知道是 A 调 B 还是 B 调 A,         │
│                也不知道线上跑的是什么:数据?调用?事件?      │
│                                                              │
│  ③ 抽象层次混乱 一张图里,整个支付系统和某个工具函数          │
│                画在同一层。大小不一的概念混在一起,看的人       │
│                不知道该用什么颗粒度理解。                       │
│                                                              │
│  ④ 框太多      四十个方块挤在一页,信息量爆炸,                │
│                看的人直接放弃。                               │
└─────────────────────────────────────────────────────────────┘
```

我们要做的就是治好这四宗罪：清晰的边界、箭头表明方向与含义、一张图只用一个抽象层次、框的数量受控。

吐槽一下，AI 在画图的时候就经常这样，密密麻麻的线，光看就犯ex，所以一定要学会画图😾

## C4模型

核心思想就和你用地图软件一样，查路线行程时，你不会用同一个缩放级别看所有东西吧？设想你被扔到了异世界，此时你按下M查看地图，你首先看到的是整个国家的地图，你知道了你在哪个城市，不是一上来就把王都某家酒馆的内部布局展示给你，要找任务地点，放大到市区图看主干道，再放大到街道图看具体怎么走。

不同层次的信息，应该在不同的视图表达

```text
   缩放级别        C4 层次              画的是              给谁看

   🌍 世界地图  →  ① Context 上下文   整个系统 + 周边     所有人
                                       用户、外部系统     含非技术
                        │
                        ▼ 放大,钻进我们的系统内部
   🏙️ 市区图    →  ② Container 容器   系统由哪几个         技术团队
                                       可独立运行的       架构、运维、
                                        大块组成          技术负责人
                        │
                        ▼ 放大,钻进某一个容器内部
   🛣️ 街道图    →  ③ Component 组件   一个容器内部         开发这块的
                                       由哪些模块组成        工程师
                        │
                        ▼ 放大,钻进某一个组件内部
   🏠 楼栋图    →  ④ Code 代码        类、函数怎么组织      基本不画,
                                                          交给 IDE
```

**一张图,只待在一个缩放级别上。**  你要么画整个系统的全貌,要么钻进某一块看它内部,**绝不在一张图里混着画**

### 第一层：Context：系统上下文

这是缩放到最远的一层，整个系统就是中间一个框，里面有啥先不管，周围画的是：谁在用它，比如用户。以及它要和哪些外部系统打交道，比如支付网关、邮件服务、第三方登录。

它回答的是最高层的问题:**这个系统是干嘛的?它和外面的世界怎么交互?**

![context跑腿](/images/software-architecture-notes-2/context.svg)

**给谁看:所有人,包括产品经理、老板、客服——任何不写代码但需要理解系统在生态里扮演什么角色的人**

### 第二层：Container：容器

把上面那个中间的系统框放大，钻进去，就是Container层

C4里指的是一个可以独立运行、独立部署的大块——比如一个前端应用、后端服务、一个数据库、一个缓存。判断标准很简单：它是否是一个能单独启动、单独部署的进程或存储，不是说Docker这种容器嗷

这一层回答:**我们的系统,内部由哪几个能独立运行的大块组成?它们之间怎么通信?数据存在哪?**

![image](/images/software-architecture-notes-2/container.png)

**给谁看:技术团队——架构师、技术负责人、运维**

每个 Container 通常就是一个要部署、要监控、可能要扩容的单元

**这也是架构判断最密集的一层**——拆成几个服务、数据库怎么分、要不要加缓存,取舍思想,大多体现在这张图上

### 第三层：Component：组件

再放大，深入一个Container里面，比如后端服务，看它内部有哪些模块组成，它们怎么协作

![image](/images/software-architecture-notes-2/component.png)

给谁看：给要开发这个容器的工程师

**只有当某个 Container 复杂到值得拆解时,才需要画它的 Component 图——简单的就别画了。**

### 第四层：Code：代码

这个就是码农敲的代码，具体到类，函数怎么组织

这一层基本不用手画，代码本身就是Code图，必要时可以借助 IDE 等工具查看

朴素的智慧：**别去手工维护一份代码一改就过时的文档。**  你的精力,该花在 Context 和 Container 这种相对稳定、又最需要沟通的层次上

## 画图的基本元素

```text
   ┌─────────┐
   │  框     │   = 一个有职责的东西。
   └─────────┘     它得能回答:你是干嘛的。一个系统、一个服务、
                   一个模块都行,但同一张图里,所有框的尺度要一致。

       ───▶       = 箭头 = 一段关系。
                   关键:① 一定有方向,谁主动找谁;
                        ② 一定标含义,线上跑的是调用?数据?事件?
                   没方向、没含义的线,是烂图的头号来源。

   ┌ ─ ─ ─ ─ ┐
   ┊ 边界    ┊   = 一条分界线。
   └ ─ ─ ─ ─ ┘     圈住属于一起的东西。它可能是:
                   • 部署边界:这些跑在同一台机器/集群里
                   • 信任边界:框内是我们可信的,框外的输入都不可信
                   • 系统边界:哪些是我们的,哪些是外部的
```

不要忽略边界，它恰恰能体现架构思维，一条边界,常常同时意味着部署在哪和信任到哪，这是一条把我们的系统和外部输入分开的信任边界。**边界画在哪,往往就是安全和部署决策的所在。**

## 画图需注意

1. **一张图,只用一个抽象层次：** 别在画整个系统的图里,突然塞进一个具体函数。**要么都是大块,要么都是模块,不许混**
2. **箭头一定标方向和含义：** 每根线都要能回答两个问题:谁找谁?为了什么?在线旁写上调用 API、读写数据、发送事件之类的几个字。**一根没标注的线,就是一个没想清楚的依赖**
3. **控制框的数量,控制在 7±2。一张图超过 9 个框,就该考虑:是不是该往上抽一层、或者拆成两张图了。**  信息要分层喂,不是一次性砸过去
4. **先画 Context,再往下钻。**  永远从最宏观的那张图开始,确认系统和外界的关系对齐了,**再**钻进去画 Container。**自顶向下,别一上来就陷进某个组件的细节里**
5. **图是给人看的,不是给机器看的。**  时刻问自己:我的读者是谁?他需要这个信息吗?给老板看的 Context 图里别出现技术黑话;给工程师看的 Container 图别为了简洁省掉关键的数据流。**永远为你的读者画图。**

如果让我现在重新画一张架构图

画图之前先问三个问题：

1. 这张图准备给谁看？他最关心什么？（大部分时候是给我自己看）
2. 我要解释的是系统与外界的关系、系统内部的组成，还是某一次具体请求的执行过程？
3. 哪些细节是必须出现的，哪些细节反而会干扰理解？

如果目标只是向别人介绍整个系统，那么几块核心组件和明确的关系，可能比四十个技术框更有价值。画图不是一场比谁画得更复杂的比赛，而是要用尽可能低的理解成本，把设计讲清楚。

## 省流版

- **画图的本质是对齐**,让团队所有人看到同一个系统。架构师一大半的工作是沟通,图是沟通的主力工具;想清楚却讲不明白,约等于没想清楚。**而且画图本身会逼你把含糊处想透。**
- **烂图四宗罪:没边界、箭头没方向、抽象层次混乱、框太多。**  其中抽象层次混乱最致命——就像一张地图既画整个国家又画你家楼栋。
- **C4 模型像地图软件的缩放级别**,分四层:**Context**,整个系统+周边,给所有人;**Container**,可独立运行的大块,给技术团队;**Component**,容器内的模块,给开发者;**Code**,基本不画。它的灵魂是:**一张图只待在一个缩放级别。**
- **本仓库的全景图,基本都是 Container 层的图。**  学会读它,就能读懂仓库里几乎所有系统。
- **画图的画笔只有三样:框、箭头、边界。**  框代表有职责的东西,箭头代表标方向和含义的关系,边界代表部署/信任/系统的分界。新人最易忽略边界,而它最能体现架构思维。
- **五条原则**:一张图一个抽象层次、箭头标方向和含义、控制框数 7±2、先 Context 再下钻、永远为你的读者画图。
